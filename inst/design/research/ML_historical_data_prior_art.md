# Executive summary

We surveyed a wide range of quantitative trading and research frameworks to understand how they expose *time×asset×feature* historical data for statistical/ML algorithms while preserving point-in-time (no-lookahead) semantics. Three broad architectural families emerged:

- **Precomputed dependency engines (e.g. Zipline Pipeline):**  Define a **declarative dependency graph** of factors (terms) with window lengths; an engine then computes the full panel (dates×assets) of factor values at backtest time, enforcing lifetimes and lookback rules. Outputs are materialized as a “narrow” DataFrame (one row per date×asset). This isolates data loading from strategy code and inherently respects point-in-time (no silent leaks). However, it requires pre-declaration of data needs and is inflexible to ad-hoc history queries.  
- **On-demand history APIs (e.g. QuantConnect/LEAN `History()`, Qlib DataHandler):**  Strategy code (or higher-level framework) makes explicit calls like `History(symbols, lookback)` at runtime. This approach is flexible but risks repeated I/O. Good implementations (LEAN) advise caching/rolling buffers instead of calling history each bar. Usually it returns Pandas DataFrames (often multi-index) for the requested assets and window. Causality is enforced by the API – it only returns data up to the cutoff – but correctness depends on user discipline or engine (e.g. drop-fowarding rules).  
- **Vectorized panel data libraries (e.g. vectorbt) and research harnesses (e.g. portfolioBacktest, PyBroker):** These typically assume the user has assembled a full panel (time×assets) in memory. They focus on *batch* operations (rolling windows, covariance, clustering, ML training). They often use dense numpy arrays or Pandas DataFrames. Point-in-time enforcement is up to the user: these tools rarely provide engine-level lookahead checks. They excel at speed (vectorized/Numba) but offer no built-in universe/missing-data semantics.

We also examined a few hybrid or specialized tools (PyBroker, Jesse) which combine aspects of backtest and ML.  **PyBroker** emphasizes walk-forward ML: it lets the user register train/predict callbacks, and provides caching of historical data per symbol, but each model still reads data via a DataSource. **Jesse** (crypto backtester) uses a database of candles per symbol and loads slices for each strategy route; it supports multi-symbol strategies but lacks a unified panel abstraction.

Across frameworks, *common patterns* include:

- **Dense panel with masks vs. per-symbol buffers:**  Systems like Zipline and Qlib use dense arrays (dates×assets) with boolean masks (e.g. lifetimes) or NaN for missing. Others (LEAN rolling windows, PyBroker) maintain per-symbol fixed-length buffers. Dense panels simplify multivariate ops (covariance, clustering) but require careful handling of delistings, IPOs, nontrading days. Sparse or ragged representations can skip missing, but then clustering or matrix operations become complex.
- **Pre-declaration of lookback:**  Pipeline and Qlib-like data handlers require declaring historical windows (e.g. factor window_length) upfront, enabling pre-fetch and caching. On-demand APIs allow arbitrary runtime requests but usually warn against querying inside each bar loop to avoid performance issues.
- **Separate fit vs. predict phases:**  Most frameworks distinguish (explicitly or conventionally) between “training time” when one can access full historical window and “live execution” when only current data is available. Zipline Pipeline is all precomputation (so training and execution are co-located in backtest), whereas LEAN encourages batch optimization calls on schedule (e.g. monthly). Fitted artifacts (covariances, models) are often stored externally (Python/R objects) and re-used on each rebalance.
- **Missing-data semantics:**  Frameworks diverge here. Zipline Pipeline enforces lifetimes (no asset appears outside its IPO/delist) and typically yields NaNs for dates when an asset exists but has no price (closing the market fills its last price). LEAN/QuantConnect by default *forward-fills* (except if an asset had **no** trades at all then it returns **no data** for that symbol). Qlib delegates most imputation/drop rules to user-defined “processors”. PortfolioBacktest (R) uses quantmod/xts semantics (generally NA for missing) and assumes portfolio functions will handle it.  
- **Caching and memory layout:**  Data is commonly cached in memory or disk for reuse. Zipline Pipeline avoids recomputing lifetimes/masks for each factor and uses an execution plan to free memory aggressively. LEAN allows caching history requests on first use or preloading via warm-up. PyBroker emphasizes caching of raw data and intermediate indicators. Vectorbt encourages using contiguous NumPy arrays (optionally memory-mapped) for speed. Multi-dimensional slicing is key: Pipeline uses lazy AdjustedArray views for windows, while vectorbt relies on numpy broadcasting.

**Leading evidence:**  Zipline’s Pipeline is the classic example of a precomputed panel engine with strong point-in-time guarantees. Qlib exemplifies a modern ML-centric data handler: it assembles datasets via Python DataFrames and distinguishes train vs. infer processors for causal correctness. LEAN’s history API is widely used in industry and demonstrates the pitfalls of history queries (e.g. fill-forward semantics). Jesse and PyBroker, though less documented, suggest a pragmatic approach of loading exactly the needed data into memory for each strategy, often via user-managed buffers.

**Key anti-patterns:**  One is *silent universe leakage*: e.g. auto-forward-fill of missing prices can hide entry/exit dates. Another is *repeated history queries* each bar (performance killer). We also warn against *opaque imputation*: users should be forced to decide how to treat NaNs rather than engine doing it under the hood. 

**Unresolved issues:**  How best to represent a truly 3D panel (time×asset×feature) in memory remains open: dense 3D numpy/Arrow arrays vs. separate 2D planes vs. in-memory databases. Also, versioning of fitted artifacts (for provenance) is generally manual. The survey did not find an “industry consensus” on a universal format for marking data as stale or instrument-excluded.

**Relevance to ledgr:**  The strongest model is a **hybrid approach**: let an engine provide the **causal data projection** (time×asset panel per feature, with masks), but let modeling/training libraries handle the fit and features. Ledgr can learn from Pipeline’s strict domain/lifetimes enforcement and from Qlib’s DataHandlerLP design, while avoiding leaner’s pitfalls (uncontrolled history calls).  

No single competitor provides an out-of-the-box solution exactly matching ledgr’s needs, so ledgr’s design will likely involve combining patterns (e.g. a pre-declared panel with caching, plus user-facing fit callbacks) rather than copying any one system wholesale.

# Detailed system reviews

## Qlib

**Internal representation (5.1):**  Qlib’s **DataHandlerLP** class uses Pandas DataFrames as its core data structure. When initialized, you supply a list of instruments and time range; DataHandlerLP will produce three DataFrames: raw data (`DK_R`), infer-set (`DK_I`), and learn-set (`DK_L`). In practice, each DataFrame has a **multi-index** (date, instrument) or equivalently a date index and columns for assets, storing OHLCV and feature values. The on-disk format is a custom “.bin” array-based store, but in-memory work is done via Pandas. 

**Historical-window mechanics (5.2):**  You typically fetch history via `DataHandlerLP.fetch(...)`, which returns a Pandas DataFrame covering the specified date slice. All data is preloaded/processed up to `end_time` at initialization (or cached). Internally, DataHandlerLP has learn- and infer-processors: these can “learn” parameters (e.g. normalization means) on a fit range, then apply them to new data. Thus, Qlib allows slicing windows arbitrarily by date as long as they fall within the loaded range. In terms of cost, fetching a DataFrame slice is typically cheap if data is in-memory. Users may call `DataHandlerLP.from_df()` to wrap an existing DataFrame and then fetch from it.

**Multivariate access (5.3):**  Qlib natively supports full panels: its DataFrames can encompass many assets (columns) and features simultaneously. The pipeline works in cross-section: e.g. building a label (future return) for all instruments is natural. Covariance or clustering is done by the user on the output DataFrames. All features and labels can be merged into one wide DataFrame indexed by date×asset. The only hitch is when assets join/leave: those show up as NaNs in the wide panel. But Qlib explicitly tracks instrument lifetimes via its stock pool configuration.

**Changing universes (5.4):**  The instrument list is supplied at DataHandler creation. For dynamic universes, Qlib uses an **InstrumentProvider** (like `ParamProvider`) to define which instruments are considered. If an asset has no data for part of the range (before IPO or after delist), the DataFrame rows for that symbol and time will be absent or NaN. Qlib has no hidden “fill”. The DataHandler has a `drop_raw` flag that, if true, will drop assets with no data when constructing the pipeline, reducing memory. In practice, users often write segments (“train”, “test”) that slice times and allow algorithms to only see current-universe assets.

**Missingness semantics (5.5):**  Qlib treats missing values explicitly. The raw DataFrame may contain `NaN` if data is missing. Users can plug in processors like `Fillna`, `DropnaFeature`, `DropnaLabel`, etc.. By default, no silent fill-forward occurs: if an OHLCV series has gaps (e.g. weekends or data issues), they remain NaN. Qlib expects the user/model to decide. Stale/backfilled values do not enter the processed DataFrames unless a processor inserts them.

**Point-in-time guarantees (5.6):**  Qlib’s design is research-focused, not an execution engine. The DataHandler ensures that only historical data up to each date is used in `DK_I` vs `DK_L`. For example, a trainer pipeline might use `fit` on dates <t, and prediction pipeline uses only DK_I up to t. However, this guarantee largely depends on how the pipeline is coded; Qlib does not enforce lookahead for arbitrary user code. It does provide tools to **simulate** true point-in-time by using separate infer/learn flows, but the user must apply them properly. Overall, Qlib provides the raw building blocks (data segmented by time) but leaves strict causality enforcement (e.g. not leaking future means into training) up to the user’s segmentation.

**Precompute vs runtime (5.7):**  Qlib **precomputes** everything before model training. Once you initialize the Dataset or DataHandler, all needed data (prices, factors) are loaded and processed (with possible caching on disk). There is no incremental “bar-by-bar” computation inside strategy code. In a backtest setting, one would typically call DataHandler to get the entire feature matrix for a date range, then fit models on sliding windows offline. Thus, Qlib fits well with the pattern of “prepare full panel, then apply ML”.

**Fitted-state (5.8):**  Qlib has a notion of “learnable processors” whose state can be saved. After fitting a processor (say, z-score mean/std) on a historical window, one can dump the DataHandler (or the processors) to disk (pickle). A loaded handler can then reproduce the same transforms. Any ML model trained on Qlib data would be external (e.g. a scikit-learn model), so fitted state is outside Qlib’s scope. There is no central model registry.

**Retraining schedule (5.9):**  Qlib itself does not schedule retrains. It provides a **Dataset** abstraction where you define "segments" (e.g. `{"train": (start, mid), "test": (mid+1, end)}`) and a pipeline can iterate over them. But scheduling is up to user code. For example, one might loop over quarterly segments, calling DataHandler on each. There is no built-in monthly/quarterly rebalance mechanism.

**Determinism/provenance (5.10):**  Qlib experiments can be made reproducible by fixing seeds in Python/ML code. DataHandler’s transformation (with fit processors) is deterministic for fixed config. However, Qlib doesn’t automatically record which window or seed produced which model. Users should version-control their pipelines and data. The DataHandler can save its state, but if one relies on random model initialization, that needs external handling.

**Performance (5.11):**  Qlib’s core is C/C++ optimized `.bin` files and NumPy/Pandas in Python. The DataHandler loads binary arrays with low overhead. The operations (DataFrame indexing, numpy math) can be heavy for very large universes, but Qlib is designed to be faster than naive Pandas due to its custom format. It does not expose explicit ring buffers; instead, the user typically holds only needed windows. One drawback is that DataHandler can hold large DataFrames (time×assets) in memory – but this is deliberate to allow cross-sectional ops. Memory is managed by Python; Qlib suggests caching to disk to avoid reloading on multiple runs.

**Workload probes:**

- *Covariance portfolio (A):* A Qlib user would use DataHandler to fetch 252-day returns for all 500 symbols in the universe at each month-end. The internal rep is a 2D array or DataFrame (252×500). DataHandler likely slices columns with insufficient history (assets <252 would have NaNs). No repeated DB calls – the DataHandler has everything ready (though if the engine is written in Python, one might re-run queries each rebalance; typical usage is one query per window). The asset mask (lifetimes) excludes illiquid assets. Computation cost is moderate (creating a 500×252 matrix and computing covariance). This is straightforward.

- *Clustering (B):* Qlib naturally feeds a 252×500 matrix of returns to a clustering routine (e.g. scikit-learn). The label/infer split is irrelevant here. Fitted cluster centroids live outside Qlib. If clusters are random (k-means seed), the user must seed explicitly. If universe changes, Qlib’s DataHandler simply returns a smaller matrix. The cluster labels could be merged back into a feature by aligning indices.

- *Supervised ML (C):* One would use DataHandler with a sliding “dataset” definition: e.g. for each quarter, fetch features and forward labels. Qlib has a `DatasetH` class that can deliver a *panel dataset*: input features for all (symbol, date) in the train period and corresponding labels. The history panel is simply the output DataFrame slice from DataHandler. Leak prevention relies on careful segmentation (train up to t, label beyond). Qlib itself doesn’t enforce non-overlap of label horizons; it’s on user to drop overlapping targets. The strategy would then use the fitted model on next-quarter data; Qlib does not require holding the entire training panel in memory at predict time—only the model and possibly current features.

## Zipline/Zipline-Reloaded (Pipeline)

**Internal representation (5.1):**  Zipline’s Pipeline does not expose a single “panel” object, but internally it computes 2D NumPy arrays of shape (dates × assets) for each factor. The engine then produces a **Pandas DataFrame** in “narrow” format: one row per date×asset that passed the pipeline’s screen. The DataFrame’s columns are the computed factor values. Conceptually, the data workspace is a wide matrix of booleans (lifetimes) plus wide arrays for each needed term.

**Historical-window mechanics (5.2):**  Each `Factor` (e.g. RSI, MA) has a `window_length`. Zipline computes all needed values by pulling in an AdjustedArray for each input term, then applying `.traverse()` to get sliding windows. The engine groups factors by data loader to minimize fetches. The result is that for any factor with window L, the engine fetches L extra rows of history (for every date) and then computes. It then drops those extra rows at output time. Practically, once the pipeline is set up, the engine loads *all* required history in one pass before computing (cached in workspace), so per-rebalance cost is essentially one full scan of the needed history length. 

**Multivariate access (5.3):**  Pipeline is inherently cross-sectional. Every factor computes values for *all* assets in the domain on each date. Multi-asset covariance, clustering, or cross-asset regressions are not native in pipeline (it just gives you the factor values). However, because pipeline output is a DataFrame of (date,asset,value), one can easily pivot it into a date×asset matrix for any factor. For example, `returns_df = output_df['returns'].unstack()` yields a wide 2D matrix of returns. Thus, multivariate panel access is possible *after* pipeline execution, though the pipeline engine itself focuses on one factor at a time.

**Changing universes (5.4):**  Zipline explicitly handles universe changes via its **lifetimes matrix**. The pipeline domain determines which assets are considered, typically from a static list or from asset metadata. The lifetimes matrix (date×asset boolean) masks out any asset before IPO or after delist. Pipeline’s output will simply lack rows for assets not alive on a date. If you want to handle dynamic universe (e.g. top 500 by cap), you embed that as a `Pipeline.screen` factor. But fundamentally, non-trading days/assets are excluded by the engine.

**Missingness semantics (5.5):**  Zipline’s data bundle typically forward-fills prices: if an asset had no trade on a day it existed, the price is carried from last close. Thus, factors see a continuous time series for each asset. Pipeline’s lifetimes mask is what *truly* indicates “should we output a row here or not”. There is no separate concept of “temporarily missing but fillable” vs “dead asset”: once an asset stops trading (after delist), it is removed by the mask. Otherwise, pipeline factors just get numeric data for every date the asset is tradable.

**Point-in-time guarantees (5.6):**  Zipline Pipeline enforces no-lookahead by design: the workflow only feeds past data into factors. Step 2 of its algorithm builds dependencies with extra-rows, then step 6 computes chunk-by-chunk using only data up to the current date. After computing, it explicitly discards extra history. The resulting outputs are guaranteed to use only valid historical information (the lifetimes matrix ensures no future or non-existing data is seen). Arbitrary Python code outside the pipeline, however, could violate causality; but within a pipeline run, lookahead is prevented.

**Precompute vs runtime (5.7):**  Pipelines are **precomputed** before or at the start of each rebalance. In a backtest, one typically runs the pipeline for each rebalance date (often in batch). For example, you might call `run_pipeline` for all month-ends in the backtest period; each call internally computes the entire history needed. The system doesn’t support, say, “compute factor on-the-fly inside OnData” – everything is materialized first. This is efficient when rebalance is infrequent.

**Fitted-state (5.8):**  Zipline itself does not include built-in ML models in the pipeline – it is purely deterministic factor computation. So “fitted state” is not in the pipeline, but can exist in user code. If one were to embed a model, they would typically preprocess features with pipeline, then fit model externally. Zipline has no model caching or versioning.

**Retraining schedule (5.9):**  Zipline offers no native scheduling of “fit vs execute”. It's up to the algorithm to decide when to call `run_pipeline` or train a model. Usually users schedule pipeline updates at certain intervals (e.g. monthly). Because pipeline factors can include trailing features, one could do a single daily pipeline run or multiple. The pipeline code per se does not differentiate a "fit epoch" vs "trade epoch". 

**Determinism/provenance (5.10):**  Pipelines are fully deterministic given data. The definition of each Term (factor) is code that’s version-controlled by the user. Zipline does not automatically log a provenance of pipeline runs; the user must log factor definitions, window lengths, etc. However, since pipelines are pure functions, repeating `run_pipeline` with same inputs yields identical outputs. 

**Performance (5.11):**  Zipline is optimized for batch factor computation. It avoids redundant DB loads by grouping factors by loader. Memory usage is kept in check by dropping intermediate arrays when no longer needed (reference counting). The lifetimes matrix (date×assets boolean) itself can be large but is typically a sparse mask. In practice, Pipeline scales to thousands of assets and years of data if memory allows, but it is not as fast as a fully vectorized system. The main anti-pattern is running a fresh pipeline for every single day (since it repeats work); it is meant to run only when factors change or at fixed intervals.

**Workload probes:**  

- *Covariance portfolio (A):* One would likely use the LEAN style in Zipline: in each month-end event, call `run_pipeline` for (maybe daily) returns for past 252 days (add a factor that computes returns with window 253, then pull out values). This yields a DataFrame of size ~500×252. Then compute covariance externally. Zipline would preload the 252 days of returns for all 500 (taking O(500×252) memory), then drop trailing days before output. Assets with <252 history will have NaNs in the array; cluster/user could drop them. Zipline does not repeat history load each day; it would typically be run on discrete rebalance dates only (so no unnecessary daily compute).

- *Clustering (B):* Similar to covariance: one could write a pipeline to output (say) daily log-returns, run it once to get the 252×500 panel, then run SciPy/Pandas clustering on that matrix. The pipeline already gave data per asset, so cluster seeds are entirely external. If the universe changed (e.g. at quarter boundary), one could rerun with new assets. Since pipeline factors are deterministic, cluster labels are reproducible only up to random seed in the clustering algorithm (Zipline doesn’t manage that seed).

- *Supervised ML (C):* In Zipline, one could hack a dataset: define a pipeline that outputs all chosen features for each (asset, date) in the past. For example, at quarter-end, run pipeline from start_of_history to quarter_end to get feature DataFrame, and separately generate labels (maybe via another pipeline or after pipeline). Then fit a model externally (e.g. sklearn) on that table. At run-time (on each decision bar), one might either re-run pipeline for the “now” row of features only or load precomputed feature values. In practice, Pipeline isn’t designed for continuous on-demand history, so the strategy would likely compute signals from the model output (which can be fed into pipeline if needed). The engine doesn’t supply the entire training panel to the strategy, just the result DataFrame which can be reshaped. Label leakage is prevented if pipeline only uses lagged inputs.

## QuantConnect/LEAN

**Internal representation (5.1):**  In a LEAN algorithm, **historical data lives in Pandas DataFrames or Series** when retrieved. The `History()` method returns a DataFrame indexed by time, with columns for price fields (e.g. open, high...). When multiple symbols are requested, the DataFrame has a two-level index (symbol, time) as in the docs example. Internally, LEAN’s C# engine manages data in proprietary streams and fills RollingWindow objects in C#; the Python layer converts these into Pandas structures.

**Historical-window mechanics (5.2):**  The user explicitly calls `history = self.History(symbols, periods, resolution)`. This triggers LEAN to gather the last N bars or the last T time span of data for those symbols. This is a *materialize-all-at-once* call: it pulls data from disk/caches for all requested symbols and returns it. There is no lazy view – the output is a new DataFrame each call. Repeated calls will repeat the work. In practice, one often calls `History` once per rebalance interval (not each bar) to avoid performance issues.

**Multivariate access (5.3):**  `History()` can accept a list of symbols (or even all securities in your portfolio), so it can return an N×T panel (converted to DataFrame). For example, `self.History([s1,s2], 5)` yields a DataFrame whose first index is symbol and second is timestamp. Users often then use `.close.unstack()` to get a date×asset matrix. However, LEAN does not have built-in covariance or panel ops – any clustering/PCA must be done in user code after fetching the DataFrame.

**Changing universes (5.4):**  LEAN manages dynamic universes through its *Universe Selection* framework. In a backtest, one might schedule `AddUniverse()` calls to set which assets to trade. For historical queries, one passes explicitly which symbols to include. The engine knows an asset’s trading history: if you request data before IPO, LEAN returns no rows. When symbols drop, they simply disappear. There is no implicit global asset axis – the user controls the symbol set. Survivorship bias is avoided if the user correctly sets the universe as it was known at each time.

**Missingness semantics (5.5):**  By default, **LEAN forward-fills missing data**. That is, if an asset did not trade in some minutes/days, the last known value is repeated. However, if the asset traded zero times in the entire requested window (for example, requesting minute bars at end-of-day for an illiquid stock), then History returns *no data for that symbol*. Users must be careful: a missing bar can mistakenly be interpreted as a constant price. LEAN does offer a `fill_forward=False` option in history calls to avoid this, but the default is fill-forward (C# doc [110] indicates fillForward=false can be set). In summary, missing bars are usually filled, which can distort covariance/clustering if unnoticed.

**Point-in-time guarantees (5.6):**  LEAN’s backtester itself is event-driven and only exposes past data via the History API and OnData slices. If used correctly, the strategy sees no future prices. There are no hidden leaks in History: it always uses only historically available data (aside from the forward-fill issue above). That said, the engine does not explicitly prevent e.g. writing algorithms that accidentally use forward data from `History` calls (it trusts user not to request beyond current time). But as long as the algorithm calls History up to `Time`, it is causal.

**Precompute vs runtime (5.7):**  LEAN does *not* precompute much. It expects the user to call `History()` on-demand. However, repeated calls to History for the same data can be expensive, so best practice is to call it only when needed (e.g. on a schedule). There is also an alternative: use `RollingWindow` or `Indicators` which get warmed up via an initial History and then update incrementally on each new bar. For example, one might call `History(symbol, 60, Minute)` at start to fill a 60-bar RollingWindow, then simply push each new bar via `OnData`. Thus, incremental updates are possible but must be managed by user code.

**Fitted-state (5.8):**  The engine itself does not manage fitted models. If the strategy trains an ML model, the user code must store that model (e.g. pickle it) and reuse it. Algorithms often maintain model state in instance variables. Because LEAN is multi-language (Python/C#), one must ensure any model is serializable and initializable with a given seed for reproducibility. LEAN itself does not version models or record solver settings.

**Retraining schedule (5.9):**  LEAN’s `Schedule` system allows the user to specify times (e.g. first trading day of each month) to run a function (like `Rebalance()`). A common pattern: in `Rebalance()`, call `History()` to get latest data, train/retrain portfolio or model, then set holdings. One can thus explicitly separate "retrain on month-end" vs "rebalance each day". There is no built-in “monthly covariance” – it’s all user-scheduled. Many example algorithms use monthly or quarterly retrain via `Schedule.On(...)`.

**Determinism/provenance (5.10):**  LEAN records the data history version (via timestamps and data sources) and algorithm code. If you fix random seeds in Python or C#, repeated runs will be identical. However, it does not by default log model details or history queries. Some algorithms explicitly log the parameters used. If one uses the QuantConnect cloud, at least data and code are in version control. But for reproducibility, any randomness (e.g. k-means seed) must be controlled by the user.

**Performance (5.11):**  LEAN is optimized in C# for live speed. The `History` method can be slow for large requests, which is why docs emphasize caching via RollingWindow or indicators. Memory: history returns Pandas, so it loads requested data fully. If the lookback is 252 days for 500 symbols, that’s manageable but repeated daily calls would re-read everything. The engine avoids per-tick Python overhead by doing heavy lifting in C#. Best practice: do one bulk `History` once per month instead of 20 daily calls (to avoid O(T×L×N) cost). LEAN’s guidance and examples highlight this pattern.

**Workload probes:**

- *Rolling covariance (A):* A typical QC solution (as in docs) is: on each rebalance schedule, `History(symbols, 253, Resolution.Daily)` to get a DataFrame of close prices. Then `.pct_change()` to get returns and compute covariance. LEAN will fetch 253 rows × N=500 symbols in one go. Assets with less history simply have fewer rows. There is no unnecessary daily computation: if schedule is monthly, no repeated work on other days. However, by default LEAN would have forward-filled missing days, potentially contaminating covariance unless filtered out. The `dropna()` used in the example ([-L1240]) helps remove those initial partial rows. 

- *Clustering (B):* Similar approach: call `History(symbols, 252, Daily)` at quarter-end to get returns matrix, then apply `sklearn` clustering. The API supports any matrix, but must transform the DataFrame (`unstack`) into suitable form. No special handling of clusters in LEAN – it's user code. Random seed control would be done in user Python. If new symbols entered the universe since last fit, one would include them in the `symbols` list at that time. In Live or backtest, algorithm would have added them via Universe selection or manually at that point.

- *Supervised ML (C):* One would use LEAN’s `History` to build the training panel. For example, on refit date, do `history = self.History(features_list, 500, Resolution.Daily)` and align to create X and corresponding labels vector (future return). The DataFrame returned includes all requested features up to cutoff. The strategy must drop the last N days (the “forward N sessions label” horizon) from features when training to prevent leakage. After training an ML model, store it in the algorithm (or disk) and then use `Predict()` on each OnData, possibly taking the latest feature row from `History(symbol, 1, Res)`. There is no need for the strategy to retain the entire training panel beyond fit time.

## Jesse

**Internal representation (5.1):**  Jesse keeps historical data in a **relational database** (Postgres) by symbol and timeframe. During a backtest, it loads needed data into memory at startup. The strategy interacts via Candle objects. There is no single panel; each symbol has its own time series. The framework does allow having multiple “routes” (symbol+exchange pairs) and each route has its own Candle stream.

**Historical-window mechanics (5.2):**  Historical lookback is handled by calling `get_candles(symbol, start, end)` from within strategy code, which queries the in-memory cache of candles (loaded from DB). Alternatively, one preloads all history and then code simply indexes arrays or uses RollingWindow equivalents. There's no built-in sliding window object provided, so users typically handle last-N logic manually. The cost of fetching past candles (once loaded) is essentially a slice of an array/dict – cheap if already in RAM. The recommended flow is to preload all candles (e.g. via `candles/import` API) and then use them as needed.

**Multivariate access (5.3):**  Multi-symbol strategies (multiple routes) run each route independently. To get cross-sectional data, a strategy can query other routes. For example, in one route’s OnBar, code can call something like `candle_other = symbol_data[other_symbol]` to peek. But there is no built-in vector interface (no F(x) that takes a matrix); it's manual. Users could, however, gather all closes of all routes into a list at each step, but that’s custom code.

**Changing universes (5.4):**  Jesse lets you **subscribe to symbols** at backtest start. You choose which symbols to include (via the config). It can add symbols dynamically with Strategy trading multiple pairs, but there's no automated universe selection. If a symbol has no data (never imported), it simply won’t appear. Markets (exchange) segmentation is explicit (e.g. Binance BTC-USDT route). When an asset’s candles run out, Jesse will treat it as dead (no more data). Survivorship bias is manual: user must ensure DB import matches historical reality.

**Missingness semantics (5.5):**  If the exchange is closed (no candles for that time), Jesse simply has no Candle object for that period. Rolling logic (e.g. checking last price) would have to be implemented by user if needed. There is no auto fill. If `get_candles` is called and data is missing (e.g. before IPO), it returns an empty list. Users must handle these cases. Typically, crypto markets never “close”, so missingness comes from asset listing/delisting.

**Point-in-time guarantees (5.6):**  The Jesse engine strictly moves forward in time bar-by-bar. Strategy code in `should_long()` or `go_long()` is only given data up to the current timestamp. There is no lookahead because the engine feeds data sequentially. Moreover, candles are already timestamped (seconds resolution on crypto), so it’s inherently causal. The only way to break it would be if strategy code explicitly queries future times; in a correctly written backtest, that doesn’t happen.

**Precompute vs runtime (5.7):**  Everything is incremental: the strategy runs one bar (per subscribed symbol) at a time. There is no precomputation of all features. Indicators or rolling logic must be built inside the strategy or via libraries. For example, one might use `ta-lib` to compute a moving average on the fly by feeding the RollingWindow of last N candles. Precomputation is limited to the data import step.

**Fitted-state (5.8):**  Jesse does not natively include ML. If a user trains a model, they can save it to disk and load it in the strategy. Jesse does not track or cache model state – that’s all in user code. For stochastic solvers, since it’s Python, one could set random seeds, but Jesse itself does not enforce reproducible training.

**Retraining schedule (5.9):**  Since Jesse is script-driven, you would code `if (time to retrain) then train_model(...)`. There's no scheduler framework. Users often do “walkforward analysis” by running separate backtests (since Jesse isn’t designed to do in-simulation retraining). The given notebook examples suggest retraining is done outside (it mentions training callbacks in user code). The engine runs fixed simulation, so any retraining happens as a new experiment.

**Determinism/provenance (5.10):**  Jesse’s backtest is deterministic given the candle data and code. It logs the execution but not ML details. If one wants provenance, one must log or snapshot the script and model weights. There is no built-in mechanism to embed this.

**Performance (5.11):**  Jesse loads data from the DB up front, so it avoids DB IO during the run. Execution is in pure Python per bar, so it can be slow for high-resolution data, but crypto bars are not huge. It has no vectorization; everything is Python objects, making it slower than C/C++ engines. However, it does avoid repeated I/O. Memory usage is number of routes × retention length. It caches nothing beyond what user code does (e.g. RSI windows).

**Workload probes:**

- *Covariance (A):* In Jesse, you would need to load 500 coins worth of history. This requires importing 500 symbols and their candle histories (likely huge for crypto, but hypothetically). Then at each month-end, you’d gather the last 252 days of prices (maybe via pandas after export) and compute covariance outside. Jesse itself has no matrix ops, so the cost is born by user code. Asset with <252 days (recent coins) would simply have no data for early days (they were not in DB then). Computation would involve copying those slices into a NumPy array manually.

- *Clustering (B):* Similarly, gather returns for all coins from DB via `get_candles`, make matrix, run sklearn clustering. Jesse doesn’t help here except providing raw data quickly. Multi-coin operations are manual.

- *Supervised ML (C):* Jesse’s typical use is more rule-based. For ML, one would probably export historical price and features to an external ML pipeline (outside Jesse), then bring the model back. Jesse has “custom data” interfaces (via API) but no built-in feature panel builder. The strategy would only need to run the *predict* phase (e.g. load a model and input last N bars to get a signal). Overlapping labels wouldn’t occur naturally because Jesse is not fitting inside it. Point-in-time is ensured as long as the user passes only past bars to predict.

## PyBroker

**Internal representation (5.1):**  PyBroker stores historical data per symbol, likely as Pandas DataFrames or 1D NumPy arrays. The Strategy ties to a DataSource (e.g. YFinance) which fetches OHLCV for requested symbols and timeframes. It mentions caching of downloaded data, which implies it keeps DataFrames in memory or disk caches. There's no documented 3D structure; features are computed per symbol. 

**Historical-window mechanics (5.2):**  The user often requests data for all needed symbols at backtest start. PyBroker supports multiple timeframes (daily, minute) by performing separate fetches. When a strategy runs, it has access to all historical data at once (the notion of incremental bar feed is more abstract in PyBroker – it simulates walks). Rolling windows of indicators must be defined by the user; no built-in “last N values” class is described. Performance: fetching data from YFinance is done once and cached, so slicing it later is cheap (Pandas index slicing).

**Multivariate access (5.3):**  You can have multiple symbols in one Strategy (see examples `['AAPL', 'MSFT']`). Indicators and rules are per-symbol, but models can be multi-symbol if user code constructs a feature matrix. PyBroker’s `Strategy.add_execution(...)` can accept multiple symbols and multiple indicator definitions. It does not, however, have a built-in interface like a DataFrame of shape (dates×assets×features). Instead, one would retrieve each symbol’s feature series and manually assemble the training matrix. 

**Changing universes (5.4):**  PyBroker’s examples fix the universe at strategy creation (`Strategy(..., symbols=['AAPL','MSFT'], ...)`). It does mention “Dynamic Symbol Selection” in docs, but likely that’s manual (e.g. user code could change `ctx.algo.symbols` on the fly). There is no automated IPO/delist management – the onus is on the user to include/exclude symbols. Data missing for new symbols is just not present. No fill-forward is implied – missing days would be NaN or missing rows in the DataFrame.

**Missingness semantics (5.5):**  Raw data from YFinance will have NaN for weekends/holidays or missing hours. PyBroker doesn’t specify filling – presumably it leaves whatever YFinance gave (which usually has business-day index for stocks, no intraday fill). There are no warnings that a missing value might pass through as a signal. The documentation doesn’t highlight this, so it’s likely left to the user to clean.

**Point-in-time guarantees (5.6):**  Since PyBroker is a backtester rather than live framework, it enforces causality by splitting data into train/test windows (walk-forward). During each “test window”, it only uses data up to that point to generate signals. The sequence of calls in the example shows that `train_fn` is given *train_data* and then `exec_fn` (strategy code) uses only known data. The framework presumably does not allow reading beyond current in the simulation – it feeds bars sequentially or batches.

**Precompute vs runtime (5.7):**  PyBroker’s `Strategy.backtest()` or `walkforward()` precomputes indicators across the full backtest. The example `highest('high_10d')` likely computes a 10-day rolling high in advance for the entire series. Execution then uses these precomputed arrays. Models are trained once per window (in walkforward). There is no per-bar Python loop fetching data – it’s vectorized or done in compiled code.

**Fitted-state (5.8):**  PyBroker has an explicit `model()` registration: you define `train_fn`, PyBroker fits the model and stores it (return value of train_fn). This model object is then used in `exec_fn` to produce predictions. It says “caching of models”, implying it saves models to disk for reuse between runs. However, there’s no formal versioning or hash. Retraining repeats `train_fn` per new window. Stochastic fits would have to fix seeds within `train_fn`.

**Retraining schedule (5.9):**  Walkforward calls take parameters `windows` and `train_size`: it splits the date range automatically and runs `train_fn` at each window. So retraining is built in as part of the backtester. Alternatively, for fixed rebalance, user could call `strategy.backtest()` with a rebalancing config. Either way, PyBroker does handle “train quarterly, trade monthly” by dividing the dataset accordingly.

**Determinism/provenance (5.10):**  If `train_fn` is deterministic (seeded) and data is fixed, the walkforward results are deterministic. PyBroker does not automatically log code, but since everything is Python, one would version control the notebook or script. Predictions from the model are just part of the result object. No built-in experiment tracking beyond what the user does.

**Performance (5.11):**  PyBroker claims to be “super-fast” via NumPy and Numba. It likely stores data as NumPy arrays to avoid Python overhead in inner loops. For each strategy, it parallelizes and numbas loops over symbols/time. It also caches data in memory, so only one fetch per symbol per run. The possible anti-pattern is caching everything in Python objects (slower), but they explicitly say they avoid that.

**Workload probes:**

- *Rolling covariance (A):* PyBroker could fetch the 252-day returns via its data source (e.g. `YFinance`). Once downloaded (one-time cost), it can be stored in a NumPy array shape 252×500. But PyBroker doesn’t provide a built-in Cov solver; one would manually compute cov. The big O cost is in the initial download of 500 tickers (which may be parallelized as indicated). It won’t “do it daily”: likely the user triggers the backtest only on schedule.

- *Clustering (B):* Build the returns matrix from cached data (like above), feed into `sklearn.cluster`. PyBroker doesn’t cache or output cluster labels as features natively, so any using of cluster results as signals must be done in user code between runs or via custom indicator.

- *Supervised ML (C):* PyBroker explicitly supports ML: in `strategy.add_execution(..., models=[my_model])`, they register a model. The system then calls `train_fn` with (symbol, train_data, test_data) and expects a model object. The framework then feeds predictions to the strategy via `ctx.preds('my_model')`. Importantly, the full training panel (features + labels) is passed to `train_fn`, so the user can do Pandas modeling as usual. Point-in-time is handled by splitting train/test windows. The runtime code `exec_fn` only sees the prediction outputs for each symbol (not full training panel). Overlapping labels: PyBroker likely only uses non-overlapping time windows as per train/test split. If user wanted sliding re-training, they’d specify smaller steps. The strategy callback never sees the whole panel, only predictions.

## vectorbt

**Internal representation (5.1):**  Vectorbt operates on *arrays* and Pandas objects. Typically one starts with a Pandas Series/DataFrame for each asset (or YFData yields one). Vectorbt then constructs `Index` objects where needed, but computations happen on NumPy/Numba arrays. It can handle multi-dimensional (3D) for parameter sweeps (e.g. many simulations×time×assets) internally. However, there is no enforced “three-dimensional panel” type; vectorbt mostly works with 2D price matrices or 1D signals. The user can think in terms of matrix, though.

**Historical-window mechanics (5.2):**  There is no history query inside vectorbt – all data must be provided upfront as time-indexed arrays. Rolling/window functions (like `rolling(window).apply()`) vectorize over the entire array. These are implemented either via Pandas (slower) or using Numba loops in vectorbt (fast). The *creation* of a rolling matrix is typically O(T×window) in cost, but due to vectorization and optional parallelism, it’s quite fast. The user does not iterate bars; instead, e.g. `vbt.Indicator.run()` returns a full matrix of indicator values for all times at once.

**Multivariate access (5.3):**  Multi-asset: yes. For example, `vbt.MA.run(prices, ...)` where `prices` is a DataFrame (time×assets) will produce multiple Series (one per asset). Covariance: one can do `bt.Indicator.run` on returns DataFrame to get a matrix. For advanced ops, vectorbt has group-by (e.g. computing stats by symbol) and broadcasting. However, vectorbt is mostly oriented to vectorizing *parallel strategy instances*, not cross-sectional regression/clustering explicitly, though the underlying array can be shaped for that. It can handle an array of shape (sim×time×asset) to compute metrics across sims.

**Changing universes (5.4):**  There is no dynamic universe concept: one defines the full DataFrame of prices/indicators before running the backtest. If an asset enters, you’d have to manually include it in the DataFrame at the appropriate time. Early times would have NaNs. Vectorbt doesn’t automatically drop/ignore assets; it expects the user to slice or mask. It assumes the data given is exactly what you want to analyze.

**Missingness semantics (5.5):**  Operates largely on raw numeric arrays with NaNs. Most computations (rollings, etc.) propagate NaN by default. Vectorbt won’t fill forward for you. If you include NaNs in the price data, your returns and indicators will be NaN at those points. The user can dropna or fillna as needed beforehand. There is no special “excluded asset” flag – it’s all by NaN.

**Point-in-time guarantees (5.6):**  There is **no** enforcement: vectorbt takes a static dataset. It is the user’s job to ensure, e.g. that when computing future-looking labels or signals, you use only past data. Typically, one would build features from a timeseries up to each date and then shift target labels by +N. But vectorbt will compute them for all time. If misused, it can inadvertently include future info (e.g. using whole-series mean). It’s simply a math library.

**Precompute vs runtime (5.7):**  Everything is precomputed. There is no runtime loop. You call, say, `Portfolio.from_signals(...)` which internally vectorizes over the entire time series. There is no per-day callback. Even if one does a walkforward analysis, vectorbt will run each model instance on full windows. There is no incremental update except manually by slicing.

**Fitted-state (5.8):**  Models are external (scikit-learn, etc.). vectorbt does not train models. If you use vectorbt’s built-in ML (limited, like linear models), they store weights internally but it’s all just returning arrays. Retraining schedule is manual: one can call vectorbt inside a loop over train/test splits. There's no persistent state inside vectorbt for that.

**Retraining schedule (5.9):**  The user must implement retraining logic. Often this is done by combining vectorbt’s data access with custom loops. Vectorbt does provide `run_combs` for parameter grids, but for time-based retraining (like “train quarterly”) you’d do your own loop and call the vectorbt functions inside it.

**Determinism/provenance (5.10):**  Purely functional – with no random, it's deterministic. If random (e.g. neural net, not in core vectortbt), you'd seed numpy. There’s no provenance tracking. The output arrays can be large, but vectorbt’s Portfolio object does have methods to serialize performance. In general, reproducibility is the user’s job.

**Performance (5.11):**  Fast. Vectorbt’s selling point is speed via NumPy/Numba. It uses contiguous arrays for calculations. For example, `portfolio.total_profit()` on a 3D array of signals is done in compiled code. Memory usage can be large if you sweep many parameters/symbols at once, but it avoids Python loops. It also can use memory-mapping (for big 3D arrays). No anti-patterns like Python per-bar loops are needed.

**Workload probes:**

- *Covariance (A):* Provide a DataFrame of last 252-day returns for 500 symbols. Compute covariance via `np.cov()` or vectorbt’s builtins. This is just a matrix multiply on 500×252, which vectorbt can do quickly with numpy. No repeated overhead per rebalance since one would do it when needed.

- *Clustering (B):* Similar: returns matrix to numpy, run sklearn. Vectorbt itself doesn't cluster, but it can prepare the array efficiently. If dynamic universe, you’d slice the DataFrame; vectorbt doesn’t auto-handle that, but Pandas can easily drop columns.

- *Supervised ML (C):* One would likely use vectorbt only for data prep. For example, get `YFData.download(symbols)` to get price DataFrames, compute feature arrays with vectorbt indicators, then manually align to build X and y for training. Vectorbt doesn’t provide a “fit” engine, so one would call Scikit-Learn outside. The training panel (X,y) is built by indexing the arrays. No leakage control is provided by vectorbt – user must do like `.drop` the future part.

## portfolioBacktest (R)

**Internal representation (5.1):**  The core input is an `xts` (time×asset) matrix of stock prices. The engine then constructs sliding windows of this matrix. Each window is typically a narrower `xts` slice. Within the R code, these are either `zoo` or `xts` objects (basically wrapped matrices).  There is also a notion of multiple datasets: one can compile a list of such panels, and portfolioBacktest will iterate over each.

**Historical-window mechanics (5.2):**  Uses explicit rolling indices: user specifies a rebalance frequency and window size. The engine internally loops over time, at each rebalance date slicing `prices[(t-window+1):t, ]` (a 2D subset) and passing that to the portfolio function. This is done in R loops or *apply functions, so it’s relatively fast in compiled code (Rcpp not mentioned, but core numeric functions are optimized). It does not keep the entire panel in memory repeatedly: each slice is a new object of size (window×N), but this is R memory so it could be heavy for very long runs.

**Multivariate access (5.3):**  By design, user’s portfolio function receives the full multi-asset window at once. So T×N is natural. Features beyond prices are not inherently included, but one could attach extra columns (like factor time series) to the xts if desired. But typically it’s just prices → weights.

**Changing universes (5.4):**  Multiple datasets (universes) are supported: the engine can randomly or sequentially sample subsets of assets to create different price panels. Within one panel, the asset list is fixed. If an asset has gaps, those are NA in xts. If the universe changes (by using a different panel), one simply runs backtest on that new xts. Survivorship: if panel is drawn from an index at random, one might have survivorship bias if not careful – but it’s user-managed.

**Missingness semantics (5.5):**  Price panels will have NA for non-trading days or holes. The code likely does not drop columns automatically – the weight function must handle NA (for example, by assigning zero weight). The documentation doesn’t specify a built-in fill; probably NA means “asset unavailable/ignored”. The engine offers `financialDataResample` to simulate missing data, but that’s user-controlled.

**Point-in-time guarantees (5.6):**  Since the input to the portfolio function is the strictly past window, future data is not visible. The engine does not cheat: it uses data only from [t-window+1 .. t] to generate weights for t+1 onward. There is no hidden lookahead – the sliding window ensures only historical data is passed.

**Precompute vs runtime (5.7):**  It is purely offline. There is no concept of “runtime OnData”. The entire backtest is a batch process: run through windows, record returns. All possible computation is basically inside each slice call. There’s no incremental update (although one could simulate that by calling lower-level APIs).

**Fitted-state (5.8):**  No explicit ML fitting. The portfolio function could, in principle, fit something on the window (it’s just user R code). The engine doesn’t store any state between windows beyond the weighting results. The user function can maintain state if they use external variables, but that’s not in-engine.

**Retraining schedule (5.9):**  The engine’s basic mode is “train on every window”. You pass a fixed `window` size and `rebalance` frequency; it automatically moves the window. If one wants infrequent training, one can set `window` large and `rebalance.period` large. There is no notion of separate training vs execution period – the window always includes all historical data up to rebalance. Overlapping training is not done by default (each window is moved forward).

**Determinism/provenance (5.10):**  Results are deterministic for given input and portfolios. The function `backtestSummary()` can save results, but code provenance is outside the package. You can save the R environment to record which portfolio functions were used.

**Performance (5.11):**  It uses vectorized math in R (via e.g. `matrixStats`, `quadprog`), and parallelization with `pbapply`. For many windows or portfolios, it can use multiple cores. No anti-patterns like nested loops – it does *apply* style or mclapply. The main overhead can be copying windows, but usually N×T matrices of moderate size (say 500×252) are fine in memory. 

**Workload probes:**

- *Rolling covariance (A):* You would include a portfolio function that ignores current prices and instead uses something like `cov(return_matrix)`. Each window slice is exactly what `portfolioBacktest()` passed, so inside the loop you could compute covariance. However, `portfolioBacktest()` expects a weight vector, not a covariance – so one would have to adapt. In practice, you’d likely use `portfolioBacktest()` to backtest different fixed allocations (e.g. minimum variance) by solving a QP in the portfolio function. The engine hands the full price slice (T×N) to that function. Assets with <T history will have NA early; `quadprog` may drop them or fail – typically, one might restrict to assets with full data.

- *Clustering (B):* Not directly applicable – there’s no clustering support. One could theoretically have the portfolio function perform clustering on the window, then pick representative assets (setting weights to 1/N for them). But the framework isn’t designed for pipelines of transforms. More likely, a user would run clustering outside of the backtest to pick assets, then test the selection with portfolioBacktest.

- *Supervised ML (C):* One would define a portfolio function that takes the window (including columns for features if added) and fits a regression/ML to predict next-period returns, then outputs weights accordingly. However, the engine doesn’t enforce no-lookahead beyond the window. Overlapping labels: since the window moves fully each step, training data slightly overlaps. The user could design train/test splits if needed, but by default it’s sliding. If label is one-day ahead return, one must shift inside the function. Training on each window is done by that function (could be slow if heavy ML). The engine itself only sees final weights, not models.

# Cross-system architectural patterns

From this survey, several patterns recur:

- **Pattern A – On-demand history API:**  Many engines (LEAN, ZL1’s `data.history()`, Jesse’s `get_candles()`) offer a callable history function. Advantage: extreme flexibility (ask for any symbols/dates on the fly). Disadvantage: encourages inefficient loops and possible lookahead. Best practice (LEAN) is to **avoid** calling history every bar; instead use persistent rolling structures. Ledgr should probably provide a controlled history interface (maybe only on rebalance) rather than encourage arbitrary use in callbacks.

- **Pattern B – Engine-managed rolling buffers:**  Examples: LEAN’s `RollingWindow`, Zipline’s `AssetExists`/pipeline mask, custom per-symbol queues. Here, the engine or strategy maintains a fixed-length queue of recent prices/indicators for each asset. Advantage: efficient, no repeated I/O after warmup. Downside: only 1D per asset, harder to feed multivariate algos. Ledgr’s design could allow strategy code to declare rolling features (like Ledgr’s existing feature system does per asset), but also provide a way to share those across assets or assemble them into a panel when needed.

- **Pattern C – Precomputed dependency graph (Zipline Pipeline):**  Define *what* needs to be computed (with windows) ahead of time. The engine then pulls all data and runs factors in topological order, producing a fully-populated panel. Advantage: strong guarantees and no double queries. Disadvantage: rigid contract (must predeclare all factors, and limited to pipeline’s API). Ledgr might adopt a variant: e.g. allow users to specify ahead which historical ranges they will need, so the engine can preload them.

- **Pattern D – ML dataset abstraction (Qlib, PyBroker):**  Data is transformed via a configurable pipeline (processors) into a “train set” and “inference set.” Users then pass these to a model training function. The engine doesn’t fit the model, just supplies the data. Advantage: clear separation of data prep vs ML. Downside: requires glue code to connect to strategy execution. Ledgr could implement a DataHandler/ML-Panel abstraction similar to Qlib’s `DatasetH`, letting user code fetch a DataFrame of features and labels for a window.

- **Pattern E – External research data (out-of-engine panel):**  Some approaches implicitly assume the user will prepare an entire panel offline and then just feed signals/weights to the engine (e.g. “I ran my ML in a notebook, now I use engine only to test trades”). This decoupling makes the engine ignorant of data origins, but risks leakage if not careful. We avoid this pattern: ledgr aims to *enforce* point-in-time, so we want the engine to supply data, not have external code peek at the future.

- **Pattern F – Hybrid (engine does windowing, external libs fit):**  Most modern frameworks do this: the engine exposes windows/panels and leaves fitting to user libraries (sklearn, PyTorch, etc.). e.g. LEAN supplies a NumPy array of returns to Covariance optimizer (external), or provides data to SciPy. Ledgr should follow: engine ensures correct panel, but model code is external. This aligns with Qlib’s philosophy and avoids reimplementing ML inside ledgr.

# Workload analysis

**Workload A (rolling covariance, 500 stocks):**  
- *Pipeline:* Would require defining a pipeline factor that outputs 252-day returns for each asset. Running it monthly would load (252×500) array in memory. Good: no repeated history fetch, assets missing history simply have NaN columns. The heavy matrix ops (cov) happen outside pipeline.
- *Qlib:* Fetching 500 cols × 252 rows via DataHandler is straightforward. Might need to convert OHLC to returns, but pipeline could do it too. DataHandler likely holds the full 500-length panel in memory once. Only one fetch per rebalance. Missing assets? Dropna option or leave NA (cov function must handle).
- *LEAN:* One `history(symbols,253)` yields a DataFrame 253×500. The example shows using `.dropna()` to remove any with insufficient data. If done daily (bad pattern), 252×500 every day would be wasteful. But if monthly, just do it monthly. The forward-fill default means incomplete data is forward-filled – must explicitly drop it.
- *PyBroker:* Likely load data via YFinance into a 500×(≥252) array once. Then compute covariance externally. If done monthly, either user splits array or reindexes. PyBroker won’t compute anything unless user code tells it. It doesn’t encourage repeated in-strategy history calls.
- *vectorbt:* Load a 500×(>=252) price array, compute returns array, call e.g. `np.cov`. It will use vectorized numpy, very fast. All data is in one array; no incremental.
- *Jesse:* Not typical for equities. If used, import 500 crypto pairs, then at each month-end manually assemble returns matrix for computing cov. It doesn’t help with panel building, so likely done offline.

**Workload B (clustering, 252×500):**  
- *Pipeline:* The pipeline could output raw returns. The clustering itself is outside pipeline, but the data comes ready. Might need to extract the DF and reshape for scipy. Fine.
- *Qlib:* Similar to covariance: use DataHandler to get returns panel, then SciPy cluster. Needs random seed control for k-means. Universe changes: just rerun DataHandler with updated instrument list. If interface, one could write a processor to run clustering per quarter and attach labels as a new feature plane.
- *LEAN:* Use `History` to get returns, cluster externally. Handling new assets: just request new symbol list each quarter.
- *PyBroker:* Same as covariance: just build NumPy matrix from cached data, cluster. All manual.
- *vectorbt:* If price DataFrame exists, compute `pd.DataFrame.pct_change()` to get 252×500 returns. Then call sklearn. Vectorized help minimal, but data is already aligned. Clustering produces label per asset; feeding that back into strategy (as a feature) would need to be done manually later.
- *Jesse:* Would require importing data and then performing clustering outside Jesse (since no pipeline). Jesse itself gives no support.

**Workload C (supervised ML):**  
- *Pipeline:* One could hack a pipeline/Dataset to output all features for all (asset,date) up to refit date, plus compute labels (e.g. future N-day returns) separately. The strategy would run pipeline up to time T, save that DF, then train a model in Python, storing it (or the outputs). On execution, one would ideally re-run pipeline for the next period inputs (or keep a sliding state) and apply model. Pipeline protects against lookahead by design, but label leakage must be managed by correctly aligning label horizon.
- *Qlib:* Ideal case for Qlib’s DatasetH: define the window, get a Pandas panel of features (in DK_I) and labels, fit model (outside Qlib). Store fitted pipeline as part of experiment state. On rebalance events, Qlib can fetch features for current date (DK_I at t) to apply model. Everything is in DataFrames, so train/test transformation parity is natural if one uses the same processors. Qlib encourages storing/fetching DataHandler objects, which helps reproducibility.
- *LEAN:* The example [59†L1233-L1240] shows building returns DataFrame and then feeding to an optimizer. Similarly, for ML one would do `history = self.History(symbols, 252)` and then feed that to `Model.fit()`. They used `.unstack()` etc. Label leakage is prevented by using `history.close.iloc[:-N]` and making labels from `history.close.shift(-N)`. Universe respect: you request only symbols in current universe each rebalance. Parity: you would use the same preprocessing on train and predict, but Lean doesn’t provide automatic pipelines for that; user must code equivalently.
- *PyBroker:* Has explicit train_fn which receives exactly the panel and label. The framework suggests `train_fn(symbol, train_data, test_data)`, implying it even does the train/test split internally. Overlapping labels are likely not an issue since walkforward splits are non-overlapping by definition (train/test sequences). Universe is whatever was given. For applying model, `ctx.preds('model')[ -1 ]` gives the latest prediction for each symbol.
- *vectorbt:* You would prepare a DataFrame of features (time×asset×features) by adding MultiIndex or a dict of arrays. Then flatten it for sklearn (stack assets or use groupby for panel). No built-in label logic. You could do `vbt.YFData`, create indicator arrays, then extract the needed slices. Parity requires user discipline (e.g. use same scaling). Vectorbt’s toolset doesn’t enforce this. The actual backtest would then use a `Portfolio` or custom loop that reads the model’s predicted weights each day; vectorbt can assist in building the initial dataset but not the workflow.
- *Jesse:* One would likely export all required data to Python or R for training, then load the model and in the strategy call it on each OnBar using only past candles. Jesse’s `Backtest` could allow passing the model weights in an “Agent” or via custom code, but this is not a standard flow. Essentially, Jesse is not geared for ML, so the pattern here is outside its normal use.

# Lessons for ledgr

From the evidence, we derive patterns:

### Worth preserving

- **Explicit point-in-time masks:**  Zipline’s lifetimes matrix and LEAN’s distinction of trading vs no-trade days show it’s critical to encode *why* data is missing. Ledgr should *explicitly* track the universe membership (active symbols) at each date, separate from actual missing value. A dense panel + boolean mask for “active” is advisable.
- **Window declarations:**  Predeclaring lookback windows (as in Pipeline and Qlib’s processors) lets the engine precompute efficiently. Encouraging strategies to declare their history needs upfront (even by Python function or metadata) could allow ledgr to pre-load data. For example, a strategy could specify “needs 252 days of returns” on setup, rather than arbitrarily calling history each day.
- **Engine-side windowing vs repeated queries:**  Both Zipline and LEAN discourage looping queries. Ledgr should provide a way to request a historical slice *once per period*, not per pulse. The strategy could be given a full `time×asset×feature` array on rebalance, not the algorithm calling `ctx.history()` many times. 
- **Data immutability:**  Ledgr’s event-sourced design requires snapshots. Qlib’s sealed data files and pipelines do this. Ledgr should enforce that historical bars/features used are immutable records (i.e. no mid-backtest edits).

### Worth investigating (spikes)

- **Dense + mask vs sparse columns:**  Many systems use dense 2D (Zipline, Qlib) with NA/False mask. Others (LEAN RollingWindow) are per-symbol. We should spike to compare: e.g. memory of 500×1000 matrix with mask vs list of 500 rollouts. Likely, dense+mask is simpler for covariance/PCA operations.
- **Declared lookback vs runtime requests:**  Spike: implement two modes in ledgr for accessing history – one where the strategy callback says “I need the last L days matrix” at rebalance (once), vs allowing `ctx$history()` calls each pulse. Compare performance and complexity. Evidence suggests declared is safer.
- **Panel representation: time×asset vs time×asset×feature:**  Many libs treat features separately (e.g. Zipline pipeline has one factor per DataFrame). Ledgr must decide: is there a single 3D panel accessible, or multiple 2D layers? Pattern D (feature planes) suggests separate 2D is common; but a 3D engine could offer more direct ML input. A spike can test ease of use: e.g. feed a 3D numpy array to a ML lib vs feed separate features.
- **On-the-fly precompute vs batch:**  Compare implementing covariance daily (expensive) vs monthly. This impacts design: should ledgr allow recompute on each bar cheaply (with caches), or require explicit schedule? The design probably should disallow unnecessary daily recompute (pattern A anti-pattern).

### To avoid

- **Silent fill-forward:**  We saw LEAN’s default forward-fill can hide a lack of data. Ledgr’s principle “no silent imputation” means we should never auto-fill missing values. If a symbol didn’t trade, indicate it explicitly (mask/None). If a feature has no new reading, it should return a special “stale” marker (like NA) that cannot be confused with a valid number.
- **Per-bar DB queries:**  Zipline’s anti-pattern of calling history in OnData is known; LEAN also warns against it. Ledgr should not expose a powerful query inside each strategy tick. If anything, it should only allow bulk queries on rebalance events.
- **Opaque preprocessing:**  Built-in pipelines that do dropna or scale without user control (auto-impute) should be avoided. Instead, ledgr can allow plugging in user-defined processors (like Qlib) so that decisions (drop vs fill vs mask) are explicit.

### Missing evidence

Our survey did not find a clear best practice for:
- **Panel dimensioning:**  Should ledgr internally store one giant 3D (time×asset×feature) dataset, or separate feature matrices? Many libraries use separate planes; no definitive winner. We might have to test memory/parallel ops.
- **Live vs backtest parity:**  Apart from instructive examples (e.g. LEAN’s RollingWindow works same in live), it’s unclear if any system automatically syncs history logic between backtest and live. Ledgr will need guidance on ensuring any history API behaves identically in paper trading.
- **Sparse vs dense trade-offs:** We know dense+mask is used, but we don’t know at what scale sparse would be better (if any). A spike measuring operations like PCA on sparse vs dense could help.
- **High-frequency cases:** Most examples were daily. How do these patterns change if working minute-level or tick-level data? Performance and semantics (no trading days meaning) could differ. We should test at higher frequency (maybe simulate 1-min data with Ledgr’s event-sourcing).

# RFC implications

Based on these findings, key questions for the design RFC include:

- **Data structure design:** Should the core history substrate be a single time×asset grid (with multiple feature “planes”), or multiple 2D planes keyed by feature? What is the right trade-off between convenience and complexity for both vectorized ops and per-feature pipelines?
- **Access pattern:** Will strategies request history *only at rebalance*, or allow some limited per-bar lookups? Do we require strategies to declare their history needs in advance (and if so, how)? 
- **Caching strategy:** Should ledgr cache entire requested panels between calls? When a panel is requested, does ledgr store it as a contiguous matrix in memory, or drop it after use? How to avoid O(T×N×F) re-materialization when not needed?
- **Missing-data encoding:** How to represent different “missingness” types? At minimum, separate masks for “nonmember” vs “nontrading day” vs “genuine missing”, or perhaps tag each NA with semantics. Can ledgr APIs expose these distinctions to the strategy?
- **Fit artifact management:** If a strategy fits an ML model, should ledgr offer any support for storing/retrieving that artifact? (Possibly just recommended patterns, since model training is external.)
- **Preloaded raw vs feature data:** Should ledgr only load raw price/volume data and expect strategies to compute features, or should it load precomputed features into the panel? Qlib leans to loading basic factors and letting processors compute others.
