# Charter: Recursive-Indicator History Spike

**Status:** Draft charter, written by Claude at the maintainer's request on
2026-10-07; awaiting peer review and maintainer acceptance. Binds nothing.
**Protocol:** `inst/design/spike_protocol.md`
**Probe:** `dev/spikes/recursive-indicator-history/probe_findings.md` (run at
`9452e9e`)
**Feeds:** the joint WS3/WS4 history-start decision that replaces Cut 9's
temporary restart rule, and the recursive-indicator RFC due in the pipeline.

## 1. Question

> For each history model ledgr can compute today (bounded window, decaying
> recursion, path-dependent recursion), how many bars of history before a
> scoring start make the values inside the window agree with the full-history
> values to a stated tolerance, and for which models does no finite number
> suffice?

That is the only question. It measures what a declared burn-in would buy; it
does not design the declaration, the hydration mechanism or an API.

## 2. Cheaper Prerequisite

> Does computing an indicator's series over the bars from `s - N` onward, with
> the same feature engine a dense run uses (`ledgr_compute_feature_series()`),
> reproduce exactly the values a public dense `ledgr_run()` sees when its
> history starts at `s - N`?

If it does, the measurement can run on the engine directly, cheaply and for
many `N`. If it does not, the spike stops; a recharter would measure through
public runs only.

## 3. Runnable Core

No package fork is needed: the question is about indicator mathematics under
the engine ledgr already runs. The core is one harness function,
`deviation(indicator, bars, s, N)`, that computes the series from `s - N` and
from the first bar, and returns the gaps on days `s` to the end. It calls only
public indicator constructors and `ledgr_compute_feature_series()`.

The prerequisite (section 2) is the core's first case: the harness value must
equal a public run's value on every common day, for every indicator.

## 4. Cases

Generated by running the core; expected answers are frozen only after it has
run, in git, with the reviewer named. Indicators:

- bounded: `ledgr_ind_sma(5)`, `ledgr_ind_sma(20)`, `ledgr_ind_ema(5)`;
- decaying recursion: TTR `EMA` with `n` of 5 and 20, and TTR `RSI(14)`
  through `ledgr_ind_ttr()`;
- path-dependent recursion: the probe's custom `running_max`.

Each is measured on two seeded price paths, the probe's sine-and-trend series
and a seeded random walk, over burn-ins `N` of 0, `stable_after`, and 2, 5, 10
and 20 times the indicator's `n` (5 for `running_max`, which has none). The
tolerances are 1e-9 and 1e-6, relative
to the full-history value.

Seven indicators times two paths is fourteen measurement series, but only
three shapes of behavior. The protocol's ten-case cap applies to the frozen
answers: one prerequisite case, plus one frozen classification per indicator.

## 5. Evidence

The runner writes one CSV row per indicator, path and `N`: the largest
absolute and relative gap inside the window, the first day within each
tolerance, and the indicator's declared `requires_bars` and `stable_after`.
Every row is derived by computation over the seeded bars; no row is narrated.

## 6. Kill And Recharter

Stop and return to the maintainer if any of these happens:

- the prerequisite fails (section 2);
- an indicator falls outside the three models, so the question's framing is
  wrong;
- answering needs availability-aware runs, which refuse every recursive
  indicator today (probe P3).

## 7. Deliverables And Gut

Exactly three executor deliverables, under
`dev/spikes/recursive-indicator-history/`:

- `spike_runner.R`, writing the measurement CSV and the prerequisite row;
- `spike_checker.R`, rerunning into a scratch directory, diffing against the
  recorded CSVs and guarding package scope (`R`, `src`, `tests`, `NAMESPACE`,
  `DESCRIPTION`, `man`, `inst/design`);
- `spike_inventory.md`, naming what was demoted, deleted and learned.

The gut forces `N = 0` (Cut 9's restart) for every row. The decaying and
path-dependent indicators must then exceed tolerance on named rows while the
bounded ones still agree after `stable_after`; merely changing bytes is
insufficient.

The closeout is the protocol's one-page terminal record under
`inst/design/spikes/recursive_indicator_history_spike/closeout.md`.

## 8. Non-Goals And Budgets

No burn-in declaration field, hydration mechanism, warmup API, gap-transition
rule, availability-mode recursion, prefix-invariance diagnostic or fn and
`series_fn` certification is decided. The measured distances depend on the
paths and parameters; per protocol section 9 they are not a general
convergence rate and never appear in a ranking.

Budgets: charter 150 lines; harness 1,500 R lines; single correction 500
lines; closeout one page. An overrun stops the spike.
